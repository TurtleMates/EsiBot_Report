\section{Architecture Overview}
\label{sec:archi_overview}

The robot's hardware architecture is organized into three processing layers and a
dedicated power layer. Figure~\ref{fig:global_archi} illustrates the overall architecture
diagram.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.62\linewidth]{images/Global_Archi.png}
	\caption{Overall \esibot{} architecture. The primary mapping sensor is the Kinect (RGB-D) and the motors are driven by the Raspberry\,Pi\,4.}
	\label{fig:global_archi}
\end{figure}

The major components are structured as follows:

\begin{enumerate}
	\item \textbf{Camera Server (ESP32-CAM):} Exposes the \gls{mjpeg} video stream \textit{via} HTTP over the local WiFi network.
	\item \textbf{Low-Level Control (Raspberry\,Pi\,4):} Directly drives the H-bridge (L298N) and reads motor odometry via the \texttt{motor\_bridge\_node} node.
	\item \textbf{Primary Mapping Sensor (Kinect):} Provides the depth image, which can be cleaned by \texttt{depth\_cleanup} and then converted into a laser scan via \texttt{depthimage\_to\_laserscan} to feed the \gls{slam} system.
	\item \textbf{Inertial Measurement Unit (\gls{imu} MPU6050):} Coupled with odometry via an \gls{ekf} filter to stabilize the robot's heading and ensure reliable positioning for Nav2.
	\item \textbf{Autonomous Exploration:} The \texttt{working\_build} repository references \texttt{m-explore-ros2}, intended to sit on top of \topic{/map} and Nav2 to automatically generate goals toward unknown frontiers.
\end{enumerate}

\section{Three-Layer Breakdown}
\label{sec:archi_layers}

\paragraph{Layer 1 --- Sensor Layer.}
Three independent data sources feed the processing layer: the ESP32-CAM (raw \gls{mjpeg}
video stream), the Kinect (depth image and RGB color image), and the wheel encoders
(pulse counting for odometry). Each source uses a distinct physical interface:
\gls{wifi} for the camera, USB for the Kinect, interrupt-driven \gls{gpio} for the
encoders.

\paragraph{Layer 2 --- Low-Level Processing (Raspberry\,Pi\,4).}
The Raspberry\,Pi\,4 hosts the \ros{} hardware interface: it reads the onboard sensors
(encoders, \gls{imu}), runs the \gls{pid} velocity control loop for both motors,
publishes odometry and telemetry topics, and receives velocity commands on
\topic{/cmd\_vel}.

\paragraph{Layer 3 --- High-Level Processing (Operator PC).}
The official diagram places computer vision (OpenCV/\texttt{depth\_cleanup}),
\pkg{slam\_toolbox}, \texttt{m-explore-ros2} and the Nav2 stack on a separate main PC,
communicating with the Raspberry\,Pi\,4 over the \ros{} network (DDS, topics/\gls{tf}).
This logical separation is made possible by the distributed nature of \ros{}: the launch
arguments (\texttt{start\_base}, \texttt{start\_kinect}, \texttt{start\_slam},
\texttt{start\_rviz}) of the \texttt{mapping.launch.py} file can be independently
enabled, which allows running the heavy nodes (\gls{slam}, Nav2) on a machine more
powerful than the Raspberry\,Pi\,4, while leaving the latter dedicated to real-time
hardware interfacing.

\paragraph{Cross-Cutting Layer --- Power.}
A battery and a regulated power distribution independently supply the actuator layer
(motors via L298N) and the compute layer (Raspberry\,Pi\,4, ESP32-CAM), as shown in
Figure~\ref{fig:global_archi}.
