\section{Kinect to \gls{slam} Pipeline}
\label{sec:slam_overview}

The system relies on a \textbf{Kinect} depth sensor to generate the environment map.
The extracted depth data is converted into a 2D laser scan. This approach provides the
standard \texttt{sensor\_msgs/LaserScan} message structure expected by the \gls{slam}
algorithm. The \texttt{mapping.launch.py} file launches and orchestrates this entire
chain (Figure~\ref{fig:slam_pipeline}).

\begin{notebox}[title={Reduced Field of View}]
	The Kinect covers $\approx57^\circ$ horizontally compared with the 180--360 degrees
	planned for a rotating radar or a panoramic LiDAR: the lateral/rear zones remain
	blind at any given instant, requiring active rotation of the robot during mapping to
	compensate.
\end{notebox}

\section{Depth Preprocessing with \texttt{depth\_cleanup}}
\label{sec:slam_depth_cleanup}

The \texttt{working\_build} branch adds the \texttt{depth\_cleanup} package, a
C++/OpenCV library independent of \ros{} and \texttt{libfreenect}. Its role is to clean
up holes in the Kinect depth data while preserving a metric \texttt{CV\_16UC1} image in
millimeters, usable thereafter by a \ros{} node that would publish a
\texttt{sensor\_msgs/Image} synchronized with \texttt{CameraInfo}. The geometry mode
adopted is \texttt{applyKinectSmoothingPipeline()}:
\begin{itemize}
	\item null pixels are treated as invalid;
	\item a $3\times3$ neighborhood fills small holes using a mode quantized into 10\,mm
	      bins;
	\item remaining holes are filled with \texttt{cv::INPAINT\_TELEA} at 20\,\%
	      resolution to limit CPU cost;
	\item the original valid pixels remain unchanged, which is checked by the package's
	      unit tests.
\end{itemize}

The \texttt{SLAM\_INTEGRATION.md} document explicitly sets the integration boundary:
\texttt{slam\_toolbox} does not consume the depth image directly, but the
\texttt{LaserScan} produced by \texttt{depthimage\_to\_laserscan}. At the current state
of the \texttt{mapping.launch.py} launch, the remapping still points to
\topic{/kinect/depth/image\_raw}. The remaining step therefore consists of inserting a
\ros{} adapter that publishes the cleaned \texttt{16UC1} image and its
\texttt{CameraInfo}, then remapping \texttt{depthimage\_to\_laserscan} to this cleaned
topic.

\section{Why the Kinect Replaces the Ultrasonic Radar}
\label{sec:slam_ultrasonic_vs_kinect}

The ultrasonic path remains present in \texttt{ultrasonic\_scan\_node}, but it is not
suited to fast autonomous driving. The \texttt{working\_build} configuration sweeps only
from $-30^\circ$ to $+30^\circ$ in $5^\circ$ steps, takes five measurements per angle,
waits 0.35\,s for servo settling, and publishes roughly 0.07 scans per second. Such a
sensor gives a sequential scalar distance per direction, strongly dependent on the
servo's instantaneous orientation: a chair, a table leg, a low obstacle or a sloped
surface can be missed or mapped to the wrong location between two costmap updates.

The article by Kamarudin et al. on the analysis of the Kinect for 2D SLAM, referenced in
Appendix~\ref{app:sources}, notes that a Kinect sensor used for 2D SLAM remains limited by
its field of view and range, but that its 3D depth data offers a richer basis for
detecting objects of varying shapes and sizes. For \esibot{}, this transforms the
problem: instead of building a costmap from a slow ultrasonic beam, a coherent LaserScan
slice is extracted from a complete depth scene updated at video rate. The ultrasonic
radar therefore still has value as a diagnostic tool or a slow local safety check, but the
Kinect is the consistent sensor feeding \texttt{slam\_toolbox}, Nav2 and autonomous
exploration.

\begin{warnbox}
	\label{sec:slam_map_state}
	The current map used by \texttt{esibot\_navigation2} (resolution 0.05\,m, origin
	$(-10,-10,0)$) corresponds, upon visual inspection, to the default TurtleBot3/Nav2
	sample hexagonal map, and not to an actual map captured by \esibot{}'s Kinect. The
	\gls{slam}~$\to$~save~$\to$~Nav2 reload chain therefore still needed field
	validation at the time of writing (Chapter~\ref{ch:resultats}).
\end{warnbox}

The \gls{rviz} configuration \texttt{esibot\_slam\_map\allowbreak.rviz} is the project's
main visualization tool (map, \topic{/scan} scan, \gls{urdf} model, full \gls{tf} tree),
rather than an integrated mapping view in the web dashboard (Chapter~\ref{ch:ihm}).

\section{Autonomous Navigation with Nav2}
\label{ch:navigation}

Autonomous navigation relies on the standard \textbf{Nav2} stack
(\texttt{navigation2.launch.py}, package \texttt{esibot\_navigation2}), loading the
static map, the \texttt{esibot.yaml} file, and orchestrating localization, costmaps,
planner, controller, behaviors, velocity smoother and collision monitor.

Localization uses \gls{amcl} (particle filter, 500--2000 particles,
\texttt{likelihood\_field} model, \texttt{DifferentialMotionModel}, initial pose not set
automatically). The local ($3\times3$\,m window) and global costmaps
\label{sec:nav_costmaps}
share a
resolution of \textbf{0.05\,m/cell}, a robot radius of \textbf{0.2\,m}, and an inflation
radius of \textbf{0.35\,m} (factor 5.0). The global planner
\texttt{NavfnPlanner} (Dijkstra, 0.5\,m tolerance) feeds the \gls{dwb} local controller,
whose bounds are summarized in Table~\ref{tab:dwb_params}.

The \gls{dwb} scoring criteria (\texttt{PathAlign} 32, \texttt{GoalDist} 24,
\texttt{BaseObstacle} 0.02, \texttt{RotateToGoal} 32) clearly favor adherence to the
global path over speed, consistent with a small-footprint indoor robot. The behavior
server exposes \texttt{Spin}, \texttt{BackUp}, \texttt{DriveOnHeading},
\texttt{Wait}, \texttt{AssistedTeleop}; a \texttt{collision\_monitor} watches a stop
disk (radius 0.1\,m), a slowdown polygon and an approach polygon (2\,s horizon) before
final transmission to \topic{/cmd\_vel}.

As noted in Section~\ref{sec:slam_toolbox_config}, the default loaded map is a generic
sample map; the Nav2 configuration itself is complete and consistent with the Kinect
pipeline, but its experimental validation on a real map still needed to be carried out
(Chapter~\ref{ch:resultats}).

\section{Autonomous Exploration}
\label{sec:slam_exploration}

The \texttt{working\_build} branch also adds \texttt{src/m-explore-ros2} as a Git
dependency. This module corresponds to the frontier-based exploration layer: it sits on
top of the \topic{/map} map, the \gls{tf} tree and Nav2, selects frontiers between known
and unknown areas, then sends successive goals to the navigator. No \texttt{esibot\_*}
launch file orchestrates it yet alongside the bringup, the Kinect and Nav2; its
operational integration must therefore verify three conditions before demonstration:
the submodule initialized in the workspace, stable \topic{/map}/\topic{/tf} topics, and
Nav2 active with either a map or online \gls{slam}.
