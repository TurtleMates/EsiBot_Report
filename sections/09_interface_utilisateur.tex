\section{Xbox Controller Teleoperation}
\label{sec:ihm_teleop}

Teleoperation relies on a wireless (Xbox-compatible) controller, driven by
\texttt{joy\_node}/\texttt{teleop\_twist\_joy} (\texttt{joystick\_drive.launch.py}),
rather than the \texttt{teleop\_twist\_keyboard} suggested in the specification.

\begin{table}[H]
	\centering
	\caption{Controller teleoperation configuration (\texttt{xbox\_teleop.yaml}).}
	\label{tab:teleop_params}
	\begin{tabularx}{\linewidth}{L{5.5cm} C{2.6cm} L{4.3cm}}
		\toprule
		\textbf{Parameter} & \textbf{Value} & \textbf{Note} \\
		\midrule
		\texttt{require\_enable\_button} & \texttt{false} & no "dead-man" button required \\
		Linear / angular axis & axis 1 (scale 0.25) / axis 3 (scale 2.4) & sticks $\to$ \topic{/cmd\_vel} \\
		Dead zone / repeat rate & 0.08 / 20\,Hz & \texttt{joy\_node} \\
		\bottomrule
	\end{tabularx}
\end{table}

The absence of a mandatory enable button means that any accidental stick deflection
immediately translates into motion, with no button to hold down --- a reduced safety
margin compared to a classic "dead-man" device (Chapter~\ref{ch:limitations}).
\texttt{joystick\_drive.launch.py} jointly starts \texttt{joy\_node},
\texttt{teleop\_twist\_joy\_node} and \texttt{motor\_bridge\_node} (max angular velocity
raised to 3.0\,rad/s, minimum duty cycle 22\,\%).

\section{\gls{ekf} Fusion --- Configuration}
\label{sec:ihm_ekf_detail}

\texttt{ekf\_odom\_imu.yaml} (\texttt{ekf\_fusion.launch.py}) configures
\texttt{ekf\_filter\_node} at \textbf{30\,Hz}, \texttt{two\_d\_mode}: from odometry
(\topic{/odom}), only velocities $(v_x,v_y,\dot\theta)$ are fused; from the
\gls{imu} (\topic{/imu/data\_raw}), only $\dot\theta$ is kept, avoiding raw acceleration
integration. The \texttt{world\_frame} remains \texttt{odom}, delegating the
\topic{map}$\to$\topic{odom} correction to \texttt{slam\_toolbox}/\gls{amcl}.

\section{Telemetry Web Dashboard}
\label{sec:ihm_dashboard}

The \texttt{imu\_web\_dashboard} node (\texttt{esibot\_dashboard}) exposes a standalone HTTP server (\texttt{http.server}) serving a single-page HTML/JS application focused on \textbf{telemetry}: roll/pitch artificial horizon, odometry trajectory (1200\,pts), and \topic{/joy}/\topic{/cmd\_vel} wheel-speed display (equation~\ref{eq:diff_drive}). The dashboard polls \texttt{GET /api/imu} (lock-protected JSON state shared between the \ros{} and HTTP threads). It does \textbf{not} display the \gls{slam} map or the video stream (Chapter~\ref{ch:limitations}).

\section{ESP32-CAM Unified Vision API}
\label{sec:ihm_camera}

\subsection{Architecture Overview}
\label{sec:ihm_camera_arch}

A dedicated FastAPI backend (\texttt{esp32-camera-computer-vision-backend}) connects to the
ESP32-CAM's \gls{mjpeg} stream and exposes four real-time video endpoints over a single
server instance running on port~5000:

\begin{table}[H]
	\centering
	\caption{Endpoints of the ESP32 Unified Vision API.}
	\label{tab:vision_endpoints}
	\begin{tabularx}{\linewidth}{L{3.2cm} L{8.6cm}}
		\toprule
		\textbf{Endpoint} & \textbf{Service} \\
		\midrule
		\texttt{/stream/raw} & Raw \gls{mjpeg} feed, no processing \\
		\texttt{/stream/human} & YOLOv8n-seg human detection \& instance segmentation \\
		\texttt{/stream/signs} & YOLOv8n road sign detection (stop signs, traffic lights) \\
		\texttt{/stream/line} & Black-tape line follower (OpenCV classical pipeline) \\
		\bottomrule
	\end{tabularx}
\end{table}

To avoid opening multiple camera connections and reduce latency, a \textbf{dedicated camera reader thread} continuously acquires frames from the ESP32-CAM and shares them with all processing modules via a shared frame buffer. Each endpoint independently reads from this buffer and applies its own processing pipeline before encoding the result as a real-time \gls{mjpeg} response.

\subsection{Object Recognition}
\label{sec:ihm_camera_objrec}

The human detection and road sign detection endpoints use \textbf{YOLOv8n} (nano variant) loaded once at server startup with a warm-up inference to pre-compile CUDA kernels and eliminate first-request latency. The YOLO model is shared between both endpoints. Human detection (\texttt{/stream/human}, confidence threshold 0.5) applies instance segmentation: detected persons are highlighted with a filled blue mask and a bounding box labelled with the confidence score, as shown in the screenshot (Figure~\ref{fig:human_detection_screen}). Sign detection (\texttt{/stream/signs}, threshold 0.4) targets road-sign classes.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.60\linewidth]{images/VisionStreams.png}
	\caption{Human detection stream (\texttt{/stream/human}): two persons detected at 0.80 and 0.83 confidence, rendered with blue segmentation masks on the live feed.}
	\label{fig:human_detection_screen}
\end{figure}

The line-follower pipeline (\texttt{/stream/line}) uses classical OpenCV: CLAHE contrast enhancement, median + Gaussian blur, morphological erosion/dilation, contour detection, and a 15-slice horizontal analysis to compute the tape's lateral deviation for potential \topic{/cmd\_vel} feedback. Overall, the system provides a \textbf{modular and scalable vision framework} combining deep learning-based object detection and classical image processing for mobile robotics, autonomous navigation, and intelligent monitoring.

\section{Implementation and Operating Procedures}
\label{ch:exploitation}

The repository provides several shell scripts (\texttt{scripts/}) that illustrate the
low-level/high-level separation, unlike the T1 test in the specification, which assumes a
single \texttt{esibot\_full.launch.py}.

\begin{table}[H]
	\centering
	\caption{Key startup scripts in \texttt{scripts/}.}
	\label{tab:startup_scripts}
	\begin{tabularx}{\linewidth}{L{3.8cm} L{7.9cm}}
		\toprule
		\textbf{Script} & \textbf{Role} \\
		\midrule
		\texttt{start\_esibot.sh} & Manual launch of the calibrator (minimal dev script) \\
		\texttt{start\_esibot\_all.sh} & Production startup: teleop, \gls{imu}, \gls{ekf}, dashboard (requires valid calibration; radar commented out) \\
		\texttt{start\_esibot\_all\_no\_\allowbreak calib.sh} & Variant without verification; also starts the ultrasonic radar \\
		\texttt{read\_pwm\_pins.py} & Direct \gls{gpio} diagnostics (PWM signals and encoder ticks) \\
		\bottomrule
	\end{tabularx}
\end{table}

\begin{notebox}[title={Kinect/SLAM pipeline started separately}]
	The scripts cover only the low-level layer. \texttt{mapping.launch.py} and \texttt{navigation2.launch.py} are started from the operator PC --- reflecting the three-layer architecture (Chapter~\ref{ch:archi_globale}).
\end{notebox}

Before any startup via \texttt{start\_esibot\_all.sh}, the script verifies a valid JSON calibration file (\texttt{\textasciitilde/.esibot/pwm\_rpm\_map.json}, generated by \texttt{motor\_calibrator}, Section~\ref{sec:cbn_calibrator}) with positive coefficients for all 4 motor directions.

\begin{lstlisting}[style=BashStyle, caption={Full startup sequence.}, label={lst:slam_nav_sequence}]
./scripts/start_esibot_all.sh      # teleop + IMU + EKF + dashboard (RPi4)
ros2 launch esibot_slam mapping.launch.py start_rviz:=true
ros2 run nav2_map_server map_saver_cli -f ~/esibot_ws/maps/test_room
ros2 launch esibot_navigation2 navigation2.launch.py \
    map:=$HOME/esibot_ws/maps/test_room.yaml use_rviz:=true
\end{lstlisting}
